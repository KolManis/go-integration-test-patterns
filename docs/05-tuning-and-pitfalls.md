# Настройка параллельности и грабли

## Два уровня параллельности в Go
- **`go test -p=N`** — сколько пакетов (процессов) идёт одновременно. По умолчанию = число ядер.
- **`t.Parallel()`** — тесты внутри пакета. Сколько одновременно — `-parallel=N`, по умолчанию `GOMAXPROCS`.
- testify suite с `t.Parallel()` внутри методов работает плохо — состояние сьюта общее. У Testo параллельность включается в `BeforeEach`, но состояние теста всё равно нельзя хранить в полях сьюта.

## Сколько ставить `-p`
- Задавать явно, а не полагаться на число ядер раннера.
- Подбирать замером: `-count=N` для нагрузки, сравнить время и стабильность при `-p=1/2/4/…`. В одной из статей лучшим оказалось «половина ядер».
- Память: каждый одновременный пакет — отдельный процесс + свои подключения к БД. Ориентир 100–300 МБ на пакет, проверить на своём проекте.
- Подключения: `пакеты × размер пула` не должно упираться в `max_connections` Postgres.
- Выигрыш упирается в самый долгий пакет: огромный пакет стоит разбить.

## Грабли, которые мы поймали
1. **Гонка миграций на пустой БД.** Два пакета одновременно делают `CREATE TABLE IF NOT EXISTS` → `duplicate key … pg_type_typname_nsp_index`. `IF NOT EXISTS` не защищает от параллельного создания.
2. **Зависание из-за очереди блокировок.** Поздний пакет делает `CREATE INDEX IF NOT EXISTS` — команда берёт блокировку таблицы, даже если индекс уже есть, и ждёт открытые транзакции соседа. Запросы соседа встают в очередь за ней. Postgres взаимную блокировку не видит (одна сторона ждёт на клиенте) — тесты висят до таймаута. Диагностика: `pg_stat_activity` + `pg_blocking_pids(pid)`.
   - Решение: миграции под `pg_advisory_xact_lock` и только если схемы ещё нет; лучше — миграции один раз отдельным шагом CI до тестов.
3. **Шаблон занят.** `CREATE DATABASE … TEMPLATE` падает, если к шаблону есть подключения.
4. **Пул исчерпан.** Тест держит транзакцию и ждёт второе подключение из того же пула — при маленьком пуле и многих параллельных тестах можно повиснуть.
5. **`AfterEach` раньше параллельных тестов.** В Testo очистку делать через `t.Cleanup`.
6. **Таймаут `go test` по умолчанию 10 минут** — при нагрузочных прогонах ставить `-timeout`.

## Как проверять стабильность
- `go test -count=20` — повторить каждый тест 20 раз.
- `-race` — гонки в самом коде.
- `-shuffle=on` — случайный порядок тестов ловит зависимости между тестами.
- Прогонять несколько раз в CI с параллельностью и смотреть на долю падений, а не на один зелёный прогон.

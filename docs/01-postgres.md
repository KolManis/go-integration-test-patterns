# Postgres: способы изоляции

## 1. Общая БД + `TRUNCATE`
Все пакеты в одной базе, после каждого теста очистка всех таблиц.
- ✅ Просто, тесты пишутся как угодно (глобальные подсчёты, «пустая очередь»).
- ❌ Только последовательно (`-p=1`). При параллельном запуске `TRUNCATE` одного пакета стирает данные другого посреди теста.
- ❌ `TRUNCATE` берёт эксклюзивную блокировку таблицы — даже «чужие» пакеты замедляются.
- Пример: `tests/01_shared_db`.

## 2. БД на пакет (процесс) из шаблона
Миграции один раз в `*_template`, каждый пакет делает `CREATE DATABASE test_<uuid> TEMPLATE …`, в конце `DROP DATABASE … WITH (FORCE)`.
- ✅ Тесты не меняются — меняется одна строка подключения. `TRUNCATE` внутри пакета остаётся и никому не мешает.
- ✅ Копия из шаблона — доли секунды, расширения (postgis и т. п.) копируются вместе с базой.
- ❌ Внутри пакета тесты по-прежнему последовательны: выигрыш растёт с числом пакетов.
- ❌ К шаблону не должно быть подключений в момент копирования — миграции накатывать отдельным соединением и закрывать его.
- ❌ Не работает, если тест ходит в отдельно поднятый сервис — у сервиса своя БД.
- Пример: `tests/02_db_per_package`, `internal/testdb/database.go`.
- Вариант без шаблона — накатывать миграции в каждую новую БД. Работает, но при сотнях миграций дорого.

## 3. Схема на воркер (вместо БД)
Одна БД, у каждого процесса своя схема: `CREATE SCHEMA test_w1`, подключение с `search_path=test_w1`.
- ✅ Схема легче базы, не засоряет список БД.
- ❌ Расширения ставятся в одну схему — нужна отдельная схема под расширения в `search_path`.
- ❌ Ломается, если в коде или миграциях прописано `public.` или очистка ищет таблицы по `table_schema = 'public'`.
- ❌ Миграции накатываются в каждую схему заново.
- В Go обычно проще БД из шаблона. Подход описан в статье KTS про pytest-xdist (см. ссылки).

## 4. Уникальные данные
Одна БД, без очистки. Каждый тест создаёт свои записи (uuid, уникальные имена) и проверяет только их.
- ✅ Параллельно и между пакетами, и внутри пакета (`t.Parallel()`).
- ✅ Единственный способ, который работает для тестов на поднятый сервис.
- ❌ Нельзя проверять «всего N записей», «очередь пуста», «воркер обработал ровно 1».
- ❌ Воркеры, сканирующие всю таблицу, трогают чужие данные — проверять только статус своих записей.
- ❌ Таблицы растут; в CI не страшно (БД каждый раз новая).
- Пример: `tests/03_unique_data`.

## 5. Транзакция на тест + `ROLLBACK`
Тест открывает транзакцию, весь код работает через неё, в конце откат.
- ✅ Быстро, чисто, глобальные проверки снова работают, тесты параллельны.
- ❌ Данные транзакции не видит никто снаружи: другой пул, горутина со своим подключением, сервис, консьюмер.
- ❌ Нельзя проверить код, который сам делает `COMMIT`/`ROLLBACK` или ожидает падения транзакции.
- ❌ Код должен принимать интерфейс «БД или транзакция» (`Exec/Query/QueryRow`).
- Пример: `tests/04_tx_rollback`, тесты `TestLimitation…` показывают ограничение.

## 6. Что ещё встречается
- **Моки репозиториев** — это уже юнит-тесты, а не интеграция.
- **In-memory БД** (SQLite вместо Postgres) — ведёт себя иначе, чем настоящая БД; не рекомендуют почти все источники.
- **Пул заранее созданных баз** — тест берёт свободную базу из пула. Требует, чтобы весь доступ к БД шёл через выданное подключение.
- **testcontainers** — отдельный контейнер Postgres на пакет. Максимальная изоляция, но дольше старт и больше памяти.

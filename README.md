# go-integration-test-patterns

Сравнение подходов к интеграционным тестам на Go с настоящей PostgreSQL: как изолировать данные
и можно ли запускать тесты параллельно.

Предмет — учебная пекарня (`internal/bakery`):
- `Repository` — заказы выпечки;
- `Oven` — фоновый воркер, который за проход печёт **все** заказы в очереди (как типичный воркер,
  сканирующий таблицу). У духовки есть время выпекания — оно имитирует ожидание сети и внешних систем,
  на которое уходит основное время интеграционных тестов.

Во всех подходах проверяются одни и те же сценарии.

## Подходы

| # | Каталог | Изоляция | Параллельность |
|---|---|---|---|
| 1 | `tests/01_shared_db` | одна БД, `TRUNCATE` перед каждым тестом | только `-p=1` |
| 2 | `tests/02_db_per_package` | своя БД из шаблона на каждый пакет | пакеты параллельно |
| 3 | `tests/03_unique_data` | одна БД, у каждого теста свои данные | `t.Parallel()` внутри пакета |
| 4 | `tests/04_tx_rollback` | транзакция на тест, в конце `ROLLBACK` | `t.Parallel()`, но с ограничениями |
| 5 | `tests/05_testo` | подход 4 на фреймворке Testo | `t.Parallel()` один раз в `BeforeEach` |

## Шпаргалка

Короткие главы по изоляции Postgres, Kafka, Redis, другим общим ресурсам, настройке параллельности и e2e, плюс ссылки: [docs/](docs/README.md).

## Запуск

```bash
docker compose up -d --wait
go test -tags=integration -p=1 -count=1 ./tests/01_shared_db/...
```

Адрес БД — переменная `TEST_DATABASE_URL`, по умолчанию Postgres из `docker-compose.yml` (порт 5433).

## CI

`.github/workflows/integration.yml` — по джобе на подход, у каждой свой Postgres (service-контейнер).
Время и результат каждой джобы пишутся в Summary прогона. Джоба «01 shared DB (-p=2)» помечена
`continue-on-error`: она показывает, что подход 1 не переносит параллельных пакетов, и может падать.

## Результаты

### Подход 1 — общая БД

- `-p=1`: стабильно зелёный.
- `-p=2`, 5 прогонов: один прогон упал — `TRUNCATE` одного пакета стёр данные посреди теста другого,
  глобальные проверки (`CountByStatus`, «духовка взяла ровно один заказ») не сошлись.
- При `-p=2` пакет без воркера стал медленнее (0,8 с → 2,5 с): `TRUNCATE` берёт эксклюзивную блокировку
  таблицы и ждёт соседние транзакции.

### Подход 2 — своя БД на пакет

`internal/testdb/database.go`: один раз создаётся `bakery_template` с миграциями (под advisory-блокировкой,
чтобы параллельные пакеты не создавали его дважды), каждый пакет делает `CREATE DATABASE … TEMPLATE`
и в конце `DROP DATABASE … WITH (FORCE)`. Сами тесты не изменились — поменялась одна строка в `SetupSuite`.

- `-p=2`, 5 прогонов: 5 из 5 зелёные.
- Время всего набора: `-p=1` — 12,1 с, `-p=2` — 7,9 с.
- Тестовые БД после прогона удаляются.
- Ограничение: тесты, которые ходят в отдельно поднятый сервис (HTTP, консьюмер в другом процессе),
  так не изолировать — сервис смотрит в свою БД, а не в базу пакета.

### Подход 3 — уникальные данные

Одна общая БД без `TRUNCATE` (`testdb.RunWithSharedPool`), каждый тест с `t.Parallel()`, создаёт свои
заказы и проверяет только их по id.

- `-p=2`, 3 прогона: 3 из 3 зелёные; пакет `oven` ≈ 2,1 с — четыре теста по 300 мс выпекания идут одновременно.
- Цена — переписанные проверки. Воркер печёт всю очередь, включая чужие заказы, поэтому:
  - «духовка испекла ровно 1 заказ» и `CountByStatus == N` по таблице больше не проверить;
  - сценарий «пустая очередь» не воспроизвести вовсе — в общей базе очередь не пуста;
  - таблица растёт от прогона к прогону (в CI это не мешает: БД каждый раз новая).

### Подход 4 — транзакция с откатом

`testdb.Tx` открывает транзакцию на тест и откатывает её в `Cleanup`. Репозиторий и духовка получают
транзакцию вместо пула (оба принимают интерфейс `bakery.DB`). Пакеты работают в отдельной БД `bakery_tx`:
там не должно быть закоммиченных данных, а подход 3 их оставляет.

- `-p=2` вместе с подходом 3, 3 прогона: 3 из 3 зелёные, пакеты ≈ 2 с.
- Вернулись все проверки подхода 1: «ровно 1 заказ», `CountByStatus`, пустая очередь. Чужие незакоммиченные
  строки транзакции не видно, а тесты идут с `t.Parallel()`.
- Ограничение показано тестами `TestLimitation…`: данные транзакции не видит никто, кроме неё самой.
  Духовка на своём пуле заказ теста не печёт; так же его не увидят HTTP-сервис, консьюмер или воркер в другом
  процессе. Не проверить и код, который сам делает `COMMIT` или открывает свои транзакции.

### Подход 5 — Testo

Тесты подхода 4, переписанные на [Testo](https://github.com/ozontech/testo) (v1.8.0): сьют `testo.Suite`,
`t.Parallel()` один раз в `BeforeEach`, параметризованный `TestBakeResult` с `CasesPastry` вместо четырёх
почти одинаковых тестов. `*testo.T` реализует `testing.TB`, поэтому `testdb.Tx` и `require` работают без изменений.

- `-p=2`, 3 прогона: 3 из 3 зелёные, пакеты ≈ 2,3–2,6 с — как в подходе 4.
- Внутри пакета 6 тестов с выпеканием по 300 мс прошли за 0,34 с: параллельность работает.
- Изоляцию данных Testo не даёт: она по-прежнему от транзакции (или от БД на пакет, уникальных данных).
  Если перенести тесты подхода 1 на Testo и включить параллельность, они упадут так же.
- Два правила для параллельного сьюта: не хранить состояние теста в полях сьюта (экземпляр общий),
  а очистку делать через `t.Cleanup` — `AfterEach` срабатывает раньше, чем закончатся параллельные тесты.

### Под нагрузкой: 6 пакетов, `-count=5` (локально)

В каждом подходе 6 пакетов (`orders`, `oven`, `bread`, `cakes`, `pies`, `cookies`), `go test -count=N`
повторяет каждый тест N раз.

| Подход | `-p` | Время |
|---|---|---|
| 1 — общая БД | 1 | 69 с |
| 2 — БД на пакет | 4 | 31 с |
| 3 — уникальные данные | 4 | 13 с |
| 4 — транзакция с откатом | 4 | 14 с |
| 5 — Testo | 4 | 14 с |

- Подход 2 ускоряется за счёт параллельных пакетов: чем их больше, тем больше выигрыш (при двух пакетах
  его почти не было). Внутри пакета тесты по-прежнему идут последовательно.
- Подходы 3–5 параллелят ещё и тесты внутри пакета — в 5 раз быстрее подхода 1.

### Грабли: миграции при параллельных пакетах

Каждый пакет при старте применял миграцию к общей БД, и это ломалось двумя способами:
- два пакета одновременно делают `CREATE TABLE IF NOT EXISTS` на пустой БД — Postgres падает с
  `duplicate key … pg_type_typname_nsp_index`;
- пакет, стартовавший позже, делает `CREATE INDEX IF NOT EXISTS` — он берёт блокировку таблицы даже при
  существующем индексе и ждёт открытые транзакции тестов соседнего пакета, а их запросы встают в очередь
  за ним. Тесты висят до таймаута, Postgres взаимную блокировку не видит (одна сторона ждёт на клиенте).

Решение (`migrateLocked`): миграция под `pg_advisory_xact_lock` и только если таблицы ещё нет.
В реальном проекте лучше применять миграции один раз до запуска тестов, отдельным шагом CI.

В CI нагрузку можно запустить вручную: Actions → integration → Run workflow, поле `count`.
